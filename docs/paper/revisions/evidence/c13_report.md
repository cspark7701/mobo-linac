# C13 — Reproduction identities and measured relative cost

## Status
Completed from archived configuration, scheduler, proposal and attempt records. No remote workflow queries or new simulations were made.

## Reproduction
Run `python scripts/analyze_revision_cost.py`. All 30 run configurations, evaluation ledgers, metrics and proposal histories are checked against completion checksums. All 4,800 evaluation timestamps are checked against their recorded durations. Per-run seed identities, effective budgets, workers, device, configuration hashes and a digest over the exact ordered attempt-manifest identities/hashes are in c13_run_costs.csv. c13_metadata.json retains the startup record, software versions and executable/static-input hashes. Seed mappings remain in supporting data, not manuscript prose.

The stage-04 startup records clean code commit `8ad6c2c4ef30d8c310eca5c1d9f663e9a47d1f52`, a hashed publication configuration, ASTRA executable and four static source/field files. All evaluation manifests agree on executable and static input identities. The template hash is recorded separately from each generated astra.in, which legitimately differs with controls. The model artifacts are float64; actual proposal histories show cuda:0 for all 540 batches. C05 documents the effective primary optimization budget (10 restarts, 1,024 raw samples, 200 maximum iterations, CUDA batch limit one), model counts, fixed-noise treatment and acquisition defaults. The startup requested one campaign thread; scheduler campaign_threads is null, so a separately enforced thread limit is not inferred from that field.

The campaign manifest overrides nominal configuration defaults: 16 initialization points, 18 batches of eight, 160 evaluations, eight workers per campaign, and one concurrent campaign. These actual settings, rather than untouched config defaults alone, define reproduction. The archived run configuration and proposal history must accompany the startup code when reconstructing the campaign. The scalarized control uses the saved balanced weights/scales; no post-hoc change to physics or seed pairing is made.

## Timing definition
run_complete.json supplies active-session elapsed campaign duration. The union of all retained evaluation start/end timestamps counts overlapping worker intervals only once. These intervals include evaluation-wrapper activity and are not isolated CPU-instruction time. The complement includes GP fitting, acquisition, dispatch/setup, parsing outside the intervals and export overhead. No independent fitting/acquisition timing split is available, so those components are not separately quantified. Sum of worker runtimes is an accounting total, never a fraction of wall time.

For each paired initialization divide method campaign duration by scalarized duration, then take the median of the ten ratios. Results are 2.737641 for constrained and 1.887952 for unconstrained MOBO, with scalarized fixed at one. The respective observed ratio ranges are [2.301773, 2.939524] and [1.655703, 2.347096]. Median non-evaluation fractions are 0.714042, 0.570026 and 0.191528. These measurements support the reported ordering for this implementation and workload. Different candidate distributions, library behavior and hardware can change cost; this is not a controlled GPU/CPU comparison or universal complexity result. Absolute durations are retained in supporting CSV only, not manuscript prose.
