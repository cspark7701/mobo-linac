## Key Changes
- **Shared device policy**: Campaigns use `get_device` for string and `torch.device` inputs. None/auto/empty selects the current CUDA device when available, otherwise CPU. Bare CUDA uses the current index; indexed requests validate available hardware. Explicit unavailable CUDA requests consistently warn and select CPU for fresh work. Unsupported types/invalid indices fail. Resume compares against saved placement and resolves strictly; it never silently migrates a checkpoint to another device. Legacy unindexed CUDA checkpoints retain the previous index-zero interpretation.
- **Tensor constants**: Objective signs, normalization scales, and normalized hypervolume reference points use the input tensor's device and floating dtype. Sequence inputs and integer tensors retain double-precision conversion. Campaign GP/acquisition tensors still use double precision; objective definitions, scales, and reference conventions are unchanged.
- **Proposal contract**: Public `ProposalResult` carries candidates, acquisition values, and metadata while preserving two-value unpacking, indexing, and length. Optimizer results must have finite `(q, D)` candidates within bounds and finite nonempty acquisition values. Invalid output is treated as an optimizer failure. Input bounds, counts, effective options, placement, and Sobol dimensions validate before optimization.
- **Fallback isolation**: Primary and reduced-budget retries use the original acquisition on its existing device. CPU fallback deep-copies the acquisition before moving the copy, leaving the supplied acquisition/GP placement intact on success or failure. Copy errors become recorded CPU-tier failures and proceed to Sobol exploration. Disabling retries still propagates the primary error. Sobol exploration uses the campaign-owned seeded stream; standalone calls without an engine use the explicit fallback_seed (default zero).
- **Audit metadata**: Every attempt records tier, optimizer device, restart/sample budgets, effective options, status, and error when applicable. Results record selected method, output/optimizer devices, fallback reason, and Sobol positions; Sobol draws also record seed. Sobol acquisition values remain zero exploration placeholders.
- **Durable history**: Campaign checkpoints store one proposal_history entry per batch, including initial/low-data Sobol batches. Pending candidates, metadata, and post-proposal Sobol/RNG state are checkpointed together. Recovery reuses metadata without duplicating the batch and checks history agreement with completed checkpoints. Atomic proposal_history.json is a derived export and a completion artifact. Older checkpoints without metadata remain resumable, including completed runs that need an empty derived history export; missing historical metadata is not inferred. Custom legacy tuple-returning proposal adapters are recorded as external proposals.
- **Logging and documentation**: Campaign, benchmark, scalarized-suite, device, GP fit, and acquisition messages use the existing logger. Quiet mode suppresses progress/debug messages while retaining warnings/errors. README documents device/resume policy, proposal compatibility, fallback limits, seeded streams, history exports, and verbosity.

## Scope and Limitations
- Nominal 200 MeV physics, thresholds, objective units/signs, campaign seeds, and archived simulation outputs remain unchanged. Existing campaign Sobol state is retained rather than replaced with a fresh stream.
- CPU isolation depends on acquisition deepcopy support. Some custom modules or BoTorch non-leaf caches cannot be copied; their failure is explicitly audited and falls through to deterministic Sobol exploration. The framework does not move the original module to repair such a copy.
- The original acquisition remains the object used by primary/retry optimization, which may update its normal internal caches. Isolation guarantees concern CPU fallback placement/state; it does not undo arbitrary mutations by a custom optimizer during primary/retry calls.
- ProposalResult preserves common tuple usage, but is a dataclass rather than a tuple instance. Code requiring an exact tuple type should unpack its two tensor values.
- Older checkpoint proposal metadata remains unknown. New batches append recorded metadata; derived exports are recoverable from checkpoint history. Resume still uses observation-based refitting and retains its existing device/RNG compatibility constraints.
- Quiet mode retains warnings/errors by design. Third-party library warnings remain governed by their own warning mechanisms.
- `docs/05_refactor_tasks/` remains ignored; local Task 12/index completion edits are absent from ordinary git status. Backend/runtime initialization remains Task 14.
